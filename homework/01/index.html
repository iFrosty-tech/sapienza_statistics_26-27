§1 Problem statement

The assignment reads, verbatim:

HMWK 1 — Example App: Public-Key Cryptography PRIVATE KEY → PUBLIC KEY in Ethereum

Notes: Elliptic-curve scalar multiplication can be viewed as a cryptographic one-way function. It is deterministic and easy to compute in the forward direction: private key k → public key Q = kG while recovering k from Q is computationally difficult. It therefore shares some properties with cryptographic hash functions, but it is based on the Elliptic Curve Discrete Logarithm Problem (ECDLP) and is used for public-key cryptography and digital signatures.

The goal is to understand the basic idea of elliptic-curve scalar multiplication, not to implement a real cryptographic system.

TASK

Write a small JavaScript/html/css program showing how a private key can be used to generate a public key using elliptic-curve scalar multiplication. (In Ethereum, the relevant elliptic curve is secp256k1).

Hints: For this exercise, use a small toy curve: y² = x³ + 7 (mod 17)

For example, use for instance the following base point: G = (1, 5) Choose for instance a small private key: k = 6

The public key is: Q = kG Define the toy curve and the base point G. Define the private key k.

Implement the basic point-addition operation. Compute and print: G, 2G, 3G, ..., kG. Or use afaster method for a larger k.

Print the final point as the TOY PUBLIC KEY.

OPTIONAL-GURU LEVEL :-) Make a slown-down visual representation of the algo (may use the canvas or SVG, whatever you like better)

== STATISTICAL EXPLORATION ==

Repeat the experiment with different values of k and, if useful, different valid base points.

Explore simple statistical properties of the resulting points, for example:

  • distribution of x and y coordinates;
  • frequency of individual values;
  • distribution of bits;
  • apparent uniformity;
  • correlations between input and output;
  • possible avalanche-like behaviour.

Discuss which of these properties are meaningful for a cryptographic one-way function and which are properties specifically associated with cryptographic hash functions.

To be written: how the assignment is read, and how the sections that follow answer its three parts, the program of §3, the slowed-down view of §4 and the statistical exploration of §5, before the discussion of §6.

2.2 Scalar multiplication and the discrete logarithm

To be written: scalar multiplication Q = kG as repeated addition, the order n of G and the cyclic subgroup it generates, and the elliptic-curve discrete logarithm problem of recovering k from Q, with the generic cost of about \sqrt{n} operations.

2.3 From a private key to an Ethereum address

To be written: the private key as an integer in [1, n - 1] on secp256k1, the public key Q = kG, and the address as the last 20 bytes of the Keccak-256 digest of the coordinates of Q: the one-way step is the scalar multiplication, the hash comes after.

§5 Statistical exploration

5.1 Experimental design

To be written: why the experiment is repeated on a ladder of curves rather than on the toy curve alone; the difference between an exhaustive enumeration of every k from 1 to n - 1, whose results are exact population values, and the sample of {{fig.params.sampleN}} keys on secp256k1, whose results are estimates; Keccak-256 of the same keys as the baseline of a hash function; and the null hypotheses tested in §5.2 to §5.7.

5.2 Distribution of the coordinates

To be written: the null hypothesis that x and y are uniform on the integers of [0, p), the chi-square statistic, and what Figure 5 shows for each curve, for secp256k1 and for Keccak-256.

5.3 Frequency of individual values

To be written: how often each field value occurs as a coordinate, against the Poisson law of a random function, and why the multiplicities of x and y are fixed by the residue of p modulo 3 (Figure 6); the observed multiplicities on \mathbb{F}_{1051} are {{fig.occupancy.O1051.xMultiplicity}} for x and {{fig.occupancy.O1051.yMultiplicity}} for y.

5.4 Distribution of bits

To be written: the proportion of ones at each bit position of x, compared with one half and with the exact proportion q_j of a uniform integer on [0, p), which differs from one half in the top bits because p is not a power of two; the monobit and chi-square tests on the 256 bits of secp256k1 and Keccak-256 (Figure 7).

5.5 Apparent uniformity

To be written: whether the multiples kG spread evenly over the plane, the two-dimensional cell test and its reference, the mirror symmetry that every subgroup must show, and what the eye can and cannot see in Figure 8.

5.6 Correlation between input and output

To be written: whether the output kG carries any trace of the input k: the periodicity of the sequence, the coefficients of Table 5, the exact zero of r(k, x) over a full orbit and the exact one of the mirror pairs, both consequences of (n - k)G = -kG, and the sampled estimate on secp256k1.

5.7 Avalanche-like behaviour

To be written: how many output bits change when one bit of k is flipped (Figure 10), the strict avalanche criterion of each pair of input and output bits (Figure 11), and the decisive difference of Table 6: for scalar multiplication the new output follows from the old one by a single point addition, for Keccak-256 it does not.

5.8 The cost of inversion

To be written: the one property a statistical test of the outputs cannot see, the cost of recovering k from Q: exhaustive search and baby-step giant-step on curves of growing prime order (Figure 12), the effect of a smooth order such as {{fig.ladder.T17g.n}} = {{fig.ladder.T17g.factors}} (Pohlig and Hellman), and the extrapolation to secp256k1.

5.9 Summary

To be written: a reading of Table 7, property by property, as the bridge to the discussion of §6.

App. Reproducibility

Every figure, table and statistic on this page is computed when the page is built, from the parameters, seeds and sample sizes printed here, and can be recomputed by anyone from the repository: npm test runs the test suite, including the values of the assignment and the published test vectors of secp256k1 and Keccak-256, and npm run build rebuilds the page. The study takes about {{fig.params.computeSeconds}} seconds (last computed {{fig.params.computedAt}}); its results are cached under node_modules/.cache/hw01/ with the key {{fig.params.cacheKey}}, a hash of the parameters, of the source of every module involved and of the figure provider itself, so that a change to any of them recomputes everything.

The curves y^2 = x^3 + 7 over the fields of 17, 1031, 1051 and 16477 elements are enumerated exhaustively: every k from 1 to n - 1 is used, so their results are exact population values, labelled Enumeration. secp256k1 cannot be enumerated: {{fig.params.sampleN}} private keys are drawn uniformly from [1, n - 1] by rejection sampling of 32 bytes from a seeded generator with seed {{fig.params.seed}} ({{fig.params.rejected}} rejections; the first key is {{fig.params.firstKey}}), Keccak-256 is applied to the same keys, and these results are labelled Simulated. The bit flips of the avalanche experiment use the seed {{fig.params.seedAvalanche}} and the random keys of the discrete-logarithm experiment the seed {{fig.params.seedEcdlp}}, both derived from {{fig.params.seed}}; the strict-avalanche matrices use the first {{fig.params.sacKeys}} keys of the sample and the discrete-logarithm experiment {{fig.params.ecdlpTargets}} keys per curve. The generator is statistical, not cryptographic, and must never produce real keys. In the browser the sampled series of Figures 5, 7 and 10 can be redrawn on {{fig.params.resampleN}} fresh keys; the caption then prints the new seed and sample size.
